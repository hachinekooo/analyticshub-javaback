# 隐私工单处理流程

AnalyticsHub 的隐私工单采用“App 建单、客服核验、后台手动执行”的模式。App 不会在用户点击后立即删除或导出数据，客服需要在管理后台完成闭环。

本文定义业务口径和操作顺序；具体 HTTP 参数见 [采集端 API](API_COLLECTION.md#9-隐私请求app-端) 与 [管理端 API](API_MANAGEMENT.md#11-隐私请求管理admin-端)。

## 角色与边界

- App：提交申请、展示工单状态。
- 客服：核对申请人、项目、用户/设备标识和请求类型，并在后台执行操作。
- AnalyticsHub：在当前项目数据库事务内执行导出或去标识化，更新工单并追加审计活动。
- 部署方：制定身份核验、通知、备份、日志和数据留存制度。

`processor=ANALYTICSHUB` 表示由内置项目数据库执行器处理。其他 processor 是扩展位，内置执行器不会替它修改数据。

## 状态与页面操作

| 当前状态 | 页面主操作 | 结果 |
| --- | --- | --- |
| `SUBMITTED`（待处理） | 开始处理 | 进入 `IN_PROGRESS`，记录处理人 |
| `IN_PROGRESS` + `DELETE` | 匿名化数据 | 二次确认工单号，成功后进入 `COMPLETED` |
| `IN_PROGRESS` + `EXPORT` | 生成导出 | 下载 JSON，成功后进入 `COMPLETED` |
| `IN_PROGRESS` + 外部 processor | 完成处理 | 人工登记外部结果 |
| 任意非终态 | 其他操作 | 按规则拒绝或取消 |
| 终态 | 详情、通知 | 不再执行数据操作 |

推荐流程是：

```text
待处理 → 开始处理 → 处理中 → 匿名化/生成导出 → 已完成 → 通知用户
```

`COMPLETED`、`REJECTED`、`CANCELLED` 都是终态，不能再切换为另一状态。更新和执行都使用 `version` 做 optimistic concurrency（乐观并发控制），冲突时应刷新后重试。

## DELETE 的准确含义

AnalyticsHub 中的 `DELETE` 工单执行的是去标识化，不是物理删除整批分析事实。执行前必须输入完整工单号确认。

内置策略处理以下内容：

| 数据 | 处理方式 |
| --- | --- |
| 设备 | 更换 device ID 和凭据；清除历史凭据、机型和系统版本；禁用设备 |
| 事件 | 更换记录、用户和设备标识；清除 session ID 与 properties；时间降为天粒度 |
| 会话 | 更换会话、用户和设备标识；清除机型和系统版本；时间降为天粒度 |
| 流量 | 更换记录、用户和设备标识；清除 session、页面、来源和 metadata；时间降为天粒度 |
| 幂等记录 | 对关联 event ID 重新生成不可反推标识 |

继续保留：

- 已去标识化的分析事实，用于聚合统计；
- Counter 等累计结果；
- 隐私工单和不可变活动记录，用于审计；
- 操作影响数量和执行时间摘要。

工单中的联系邮箱、用户提交信息、邮件 outbox、应用日志和数据库备份不属于上述行内去标识化 SQL 的自动覆盖范围，部署方需要另外制定访问、保留和清理规则。

## EXPORT 的准确含义

导出文件只包含当前项目中匹配工单 user ID 或 device ID 的：

- 设备基本信息；
- 事件；
- 会话；
- 流量记录。

API Key、Secret 和历史设备凭据不会导出。文件由客服在浏览器中生成和下载，AnalyticsHub 不把导出文件长期保存到项目数据库。

## 审计与通知

数据操作、状态更新和审计活动在同一个项目数据库事务中完成。活动记录是 append-only（只追加）的，不允许修改或删除已有记录。

通知采用 transactional outbox（事务发件箱）：接口返回 `QUEUED` 只代表已入队，不代表邮件已经送达。最终结果应查看活动记录和 outbox 状态。

## 运营检查清单

处理前：

- 确认当前项目正确，避免跨项目操作；
- 核对申请人、user ID、device ID、联系邮箱和请求类型；
- 确认工单仍是待处理或处理中，并刷新到最新 version。

处理后：

- 检查状态为 `COMPLETED`；
- 检查影响数量与预期相符；
- 检查 `DATA_ANONYMIZED` 或 `DATA_EXPORT_GENERATED` 活动；
- 按内部流程通知用户；
- 不要把导出文件、数据库明细或凭据粘贴到公开 issue。

## 合规边界

内置策略用于降低分析数据与个人的可关联性，并保留必要运营和审计信息。是否满足某个地区的匿名化、删除权或法定留存要求，仍取决于实际埋点、自由字段、备份、日志、组织流程和适用规则；代码执行成功不等同于自动完成全部合规义务。
